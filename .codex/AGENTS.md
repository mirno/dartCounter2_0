# AGENTS.md

## Purpose
This file defines how coding agents should work in this repository: architecture boundaries, delivery workflow, and quality gates.

## Scope
- Applies to the entire repository unless a deeper `AGENTS.md` overrides a subsection.
- If instructions conflict, ask for clarification before making broad or risky changes.

## Project Context
- Environment: Nix flakes
- Architecture target: Clean Architecture + Domain-Driven Design (DDD)

## Skills (Codex)
- Use Codex Skills when a task clearly matches an installed skill workflow.
- Prefer existing skills over ad-hoc instructions for repeatable tasks.
- If a relevant skill is missing, continue with best effort and propose creating one.
- Keep skills small and focused:
  - trigger conditions
  - required inputs
  - ordered workflow
  - verification steps
  - expected outputs

## Language Strategy
- Do not stay language-agnostic when implementing changes.
- Detect the active language from touched modules and choose that ecosystem's tools and conventions.
- In mixed-language work, keep changes isolated per module and avoid cross-language coupling unless required.

## Execution Environment
- Prefer Nix shell for reproducibility:
  - `nix develop`
  - usage of direnv
- Prefer repository task runners when present:
  1. `make` (if `Makefile` exists)
  2. `remake` (if `Remakefile` exists)
  3. `just` (if `justfile` exists)

## Architecture Rules (Mandatory)
Use these conceptual layers:
- `entities` (domain model, invariants, value objects)
- `usecases` (application business flows, ports/interfaces)
- `adapters` (implementations of ports, mapping, gateways)
- `drivers` (frameworks, transport, DB, CLI, HTTP wiring)

Dependency rule:
- Dependencies point inward only.
- Allowed direction: `drivers -> adapters -> usecases -> entities`
- `entities` must not import outer layers.
- `usecases` may depend on `entities`, never on concrete frameworks.
- `adapters` can depend on `usecases` and `entities`.
- `drivers` may compose adapters/usecases but must not contain business rules.

Forbidden example:
- `drivers` importing `usecases` directly (bypassing adapter/port boundaries).

## DDD Rules
- Model domain concepts explicitly in `entities` and value objects.
- Keep ubiquitous language consistent in names (types, methods, packages, endpoints).
- Use use-case ports (interfaces) to isolate domain logic from infrastructure concerns.
- Keep entities persistence-agnostic and transport-agnostic.

## Interface and Entity Design
- Design use-case interfaces first; keep them minimal and explicit.
- Prefer behavior-focused methods over anemic data containers.
- Ensure entity invariants are enforced at construction/update boundaries.
- Reuse entity types intentionally in use-case contracts when semantically correct; otherwise map via DTOs.

## OpenAPI
- OpenAPI spec is the API contract source of truth.
- Prefer generating transport-layer/request-response models from OpenAPI.
- Keep generated models at boundaries; map to domain entities in adapters/usecases.
- Do not manually edit generated artifacts.

## Generated File Policy (Mandatory)
Do not edit generated files directly, including patterns like:
- `*.gen.go`
- `*gen.css`
- any file marked/generated by tooling headers

Regenerate with the owning tool and commit both source and generated output when applicable.

## Development Process
- Follow TDD (Kent Beck): Red -> Green -> Refactor.
- Keep changes small and trunk-friendly (trunk-based development).
- Prefer short-lived branches and frequent integration.
- Avoid large, long-running refactors without checkpoints.

## Commits, Versioning, and Releases
- Use Conventional Commits.
- Use `cocogitto` for commit validation/changelog/version automation when configured.
- Versioning scheme: Semantic Versioning (`MAJOR.MINOR.PATCH`).
- Align commit types with SemVer impact:
  - `fix:` -> PATCH
  - `feat:` -> MINOR
  - `feat!:` or `BREAKING CHANGE:` -> MAJOR

## Code Quality Gates
Before finishing a substantial change, run the best available checks:
- Formatting
- Linting
- Tests
- Build

If a linter is configured (for example `golangci-lint`), run it and fix actionable issues.

## Design Pattern Usage
- Apply patterns deliberately (see refactoring.guru catalog), not by default.
- Document pattern choice in PR/commit notes when non-trivial:
  - problem
  - chosen pattern
  - alternatives considered
  - tradeoffs

## Telemetry
- Add telemetry for operationally relevant flows (errors, latency, key business events).
- Prefer structured logs and stable field names.
- Include correlation/request IDs when available.
- Do not log secrets or sensitive personal data.

## Change Safety
- Preserve layering boundaries during refactors.
- Avoid introducing hidden coupling across bounded contexts/layers.
- When changing interfaces or entities, update tests first or in the same change set (TDD discipline).

## Agent Output Expectations
- Explain major architectural decisions in concise terms.
- Call out any boundary violations found and propose compliant alternatives.
- If required tooling is missing, state what was attempted and what is needed.
